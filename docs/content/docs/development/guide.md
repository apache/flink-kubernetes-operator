# Guide

This page collects what is needed to build, run, and debug the operator locally. The contribution process itself follows the Apache Flink [contribution guidelines](https://flink.apache.org/how-to-contribute/overview/).

## Building from Sources

Building requires Maven 3 and a JDK: the operator builds with Java 17.

```bash
git clone {{< github_repo >}}
cd flink-kubernetes-operator
mvn clean install
```

The build can be sped up by skipping the tests and building modules in parallel, one per CPU core:

```bash
mvn clean install -DskipTests -T 1C
```

### Tests and Code Style

Unit tests live next to the sources of each module and run with the build. During development they are usually scoped down:

```bash
mvn test -pl flink-kubernetes-operator                                    # one module
mvn test -pl flink-kubernetes-operator -Dtest=ApplicationReconcilerTest   # one class
```

The shell-based end-to-end tests under `e2e-tests/` need a running Kubernetes cluster with the operator deployed, and normally run through CI.

The code is formatted with Google Java Format in the AOSP style, enforced together with Checkstyle during the build:

```bash
mvn spotless:apply    # format the code before committing
mvn spotless:check checkstyle:check
```

## Local Environment

A local setup needs [Docker](https://www.docker.com/products/docker-desktop), [Minikube](https://minikube.sigs.k8s.io/docs/start/), and [Helm](https://helm.sh/docs/intro/quickstart/), installed as described under [Quick Start → Prerequisites]({{< ref "docs/try-flink-kubernetes-operator/quick-start#prerequisites" >}}).

### Building the Image

A custom image is built and pushed under a chosen `<repo>`:

```bash
docker build . -t <repo>/flink-kubernetes-operator:latest
docker push <repo>/flink-kubernetes-operator:latest
```

With minikube, pushing to a registry can be skipped by loading the image directly:

```bash
minikube image load <repo>/flink-kubernetes-operator:latest
```

or by building straight against minikube's Docker daemon:

```bash
eval $(minikube docker-env) && docker build . -t <repo>/flink-kubernetes-operator:latest
```

`eval $(minikube docker-env --unset)` switches back to the local daemon afterwards. Since minikube is itself a Docker container, `minikube ssh` opens a shell inside it for low-level inspection, checking the loaded images or adding a hostPath mount for example.

### Installing the Operator Locally

The admission webhook runs by default and needs cert-manager for its TLS certificate, installed once per cluster:

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
```

Alternatively, `--set webhook.create=false` on the install below skips the webhook and with it the cert-manager requirement, as covered under [Cert Manager]({{< ref "docs/deployment/helm/cert-manager" >}}).

```bash
helm install flink-kubernetes-operator helm/flink-kubernetes-operator \
    --set image.repository=<repo>/flink-kubernetes-operator --set image.tag=latest
```

`helm uninstall flink-kubernetes-operator` removes it again.

The chart can also mount additional volumes into the operator pod: `--set operatorVolumes.create=true --set operatorVolumeMounts.create=true` activates the default hostPath mount, customizable under the same keys in `helm/flink-kubernetes-operator/values.yaml`.

### Running the Operator from the IDE

The `FlinkOperator` main class runs and debugs directly from the IDE after a full Maven build. Two things must line up so the locally running operator can reach the Flink clusters it deploys:

- The operator reads its configuration from the directory in `FLINK_CONF_DIR`, `/opt/flink/conf` inside the container image. Point the variable at a local directory whose `config.yaml` overrides the REST access:

  ```yaml
  rest.port: 8081
  rest.address: localhost
  kubernetes.rest-service.exposed.type: LoadBalancer
  ```

- With the REST services exposed as `LoadBalancer`, `minikube tunnel` makes them reachable on `localhost:8081`.

## Generating and Upgrading the CRDs

The CRDs are generated by the [Fabric8 CRDGenerator](https://github.com/fabric8io/kubernetes-client/blob/master/doc/CRD-generator.md) during the build. Helm applies them on the first install only, never on upgrade or uninstall, so after changing a CRD the old one must be deleted and the chart re-installed:

```bash
kubectl delete crd flinkdeployments.flink.apache.org
```

The same applies to the other three CRDs. The production procedure, which upgrades in place instead of deleting, is documented under [Upgrading the Operator → Upgrading the CRDs]({{< ref "docs/operations/upgrade#2-upgrading-the-crds" >}}).

## CI

Every pull request runs the GitHub Actions pipeline: the build with its unit and integration tests on the supported Java versions, and the end-to-end suite from `e2e-tests/` on real Kubernetes clusters. CI must pass before a change is merged.
